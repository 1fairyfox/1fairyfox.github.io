Onboarding a project into the mesh is a direction, not a single switch, and Minecraft Automated
Driver had been honestly parked partway along it: scaffolded straight onto the shared standards from
the start — mesh-aware context file, the notes system, the git model, the quality gates — but with
its documentation site still pending. A registry marked `adopts_hub: false` recorded that gap rather
than papering over it. Today the last piece landed.

## The docs site is live, so adoption is complete

The project's documentation now serves at `fairyfox.io/minecraft-automated-driver/`, and it reads as
a page of this site rather than a separate island: the shared header, navigation and submenu, the
brand as the way home, and the shared footer, all around the project's own overview, roadmap,
security, changelog, and download pages. That was the one open requirement, so the machine registry
flips to `adopts_hub: true` — the driver is now fully onboarded, not merely listed.

## A face on the card, and data that tells the truth

The project ships an icon in its own repository, so the hub now uses it: the project card carries the
driver's own mark instead of a bare accent glyph, sized to match the rest of the Minecraft group.
The same pass reconciled the card's stale details to reality — the version had been sitting at the
day-zero scaffold number while the work had moved on to instanced client spawn, protocol bots, and
goal-level navigation, so the card now reads **v0.11.0** with a blurb that matches, and the
documentation link points at the live site instead of nowhere. Registration is the easy half of
onboarding and proves little on its own; keeping the recorded state honest is the half that matters.
